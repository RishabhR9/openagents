# Backend tests that are known to fail.
#
# The Workspace backend inherited a set of failing tests. A CI gate that ran
# pytest plainly would therefore be red forever and would teach everyone to
# ignore it. scripts/ci/check_known_failures.py reports the entries below
# separately (in the job summary) and fails the job only for failures that
# are NOT listed here — so a newly broken test still blocks a pull request.
#
# The checker is given both the pytest output and pytest's exit status: a
# missing, empty or truncated summary, or an exit status that means the run
# itself broke (2/3/4/5), fails the job. Only a real pytest exit 1 whose
# every failure is listed below passes.
#
# Captured on Windows, Python 3.11, SQLite (no TEST_DATABASE_URL), with the
# SDK installed via `pip install -e ".[sdk]"`. The backend CI job runs on
# windows-latest for the same reason. When the job moves to another platform,
# or when a recorded failure is fixed, re-capture this list:
#
#   PYTHONPATH=workspace/backend:sdk/src python -m pytest workspace/backend/tests/ \
#       -q --tb=no -rfE -o junit_family=xunit1 | tee pytest-summary.txt
#   python scripts/ci/check_known_failures.py --summary pytest-summary.txt \
#       --junit pytest-report.xml --known scripts/ci/known_test_failures.txt \
#       --pytest-exit-code 1 --pytest-rootdir workspace/backend
#
# Node ids are the ones pytest prints when it is run from the repository root.
# Remove an entry as soon as its test passes again: the checker reports
# recorded failures that now pass, so a stale list does not hide a real fix.

# ── The SDK suite is NOT part of this gate ───────────────────────────────────
# The SDK tests (tests/ at the repository root) are deliberately outside the
# pull-request gate for now:
#
#   * they need the SDK's optional dependencies (grpc, mcp, litellm) and a
#     long, network-shaped run, so they do not fit the backend job's budget;
#   * the remaining failures are platform-bound (the launcher/CLI tests look
#     for POSIX install paths and the `agn` binary), so recording them on a
#     Windows runner would list failures that do not reproduce elsewhere.
#
# This is a GAP, not a capability: the SDK suite still has no pull-request
# gate, so an SDK regression would not be caught here. The follow-up is a
# separate workflow (its own runner, its own known-failure list, the same
# checker) — it is planned work, not something this gate already does.
